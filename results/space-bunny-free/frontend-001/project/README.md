# 从芯片到 Agent

大模型部署与 Agent 应用全流程的一镜到底滚动叙事。第一章里出现的那颗芯片，会一路被装进板卡、装进服务器、装进机柜，成为 Agent 背后的那点算力；往回滚动，它沿原路退出，位置关系不变。

## 动画是怎么实现的

### 一条时间轴是唯一真相

页面只有��个状态量：`p ∈ [0,1]`，就是滚动进度。相机的注视点与推近、每个物体的世界坐标、每个零件的装配进度、每章的权重、窗口变形的进度——全部是 `f(p)` 的纯函数。

这一个决定带来了三个结果：

- **上滑必然沿原路返回**，因为返回只是重新求值同一个函数；
- **快速改变滚动方向、停在中间**，都只是换了一个 `p` 再求值一次，没有"状态机"可言；
- **导航跳转**不重建主体，只是把 `p` 平滑推过去。

Harness 层的执行信号是唯一脱离 `p` 的量：它是时间的函数而不是 `f(p)`。所以在第 07 章来回滚，执行流不会乱跳。

验证脚本对此做了断言（`verify` 第 3 项）：正向走到 `p=0.6`、反向倒回再走到 `p=0.6`、以及随机跳转到 `p=0.6`，三条路径抵达的物体与相机**逐位相同（差 0.0e+0）**。

### 物体身份是结构性的，不是跟踪出来的

场景是一棵**一次建好、永不改动的父子树**：

```
chip → card → server → rackA → cluster → root
```

「芯片落进板卡插槽」改变的是 `chip.parent`；芯片这个对象本身、它的历史世界坐标都不会被销毁。「板卡携带它进入服务器」只是父节点整体在动。**没有"跟踪"这回事——不需要在每帧重新定位任何东西**，因为它们本来就在一起。

同伴机柜在第 04–05 章陆续补齐，原机柜 `rackA` 始终在 cluster 本地坐标 `(0,0,0)`，它就是第 05 章拉远后看到的"原机柜"。

### 装配路径：先对齐，再进入、落位

每一步装配都是两段式（`engine/scene.ts` 的 `applyHover`）：

1. **悬停段**：从出发位沿一条抬高的弧线走到目标正上方，终点已经与目标坐标系对齐；
2. **进入段**：从正上方沿 −Y 压入 0.6 深度完成落位。

出发位用**世界坐标**定义，再通过 `worldToLocal` 换算到父对象局部坐标——所以无论父对象当前跑到哪里，物体都从同一个世界位置起飞。落位路径只穿孔洞，不穿外壳、底板或顶盖。

验证脚本对此做了断言（`verify` 第 4 项）：在服务器→机柜这一段扫 100 个采样点，芯片中心相对机柜顶盖平面的**最小间隙为 1.406 世界单位**，没有出现负值（即没有穿模）。

装配到位后不做任何"让路"处理：芯片被板卡挡住、板卡被服务器挡住，都是真实遮挡。

### 镜头是构图的结果，不是手调的关键帧

相机关键帧只保留**推近比例**。注视点由**构图重心**实时决定：

- 已落位的物体权重 1 —— 决定"画面要装多大"；
- 正在飞入的物体权重 0.35 —— 跟随正在装配的部件，但不会为了它把画面拉远。

于是"镜头拉远揭示集群"是自然发生的：落位的东西变多，包围盒与重心一起长大，镜头随之后退。手调的注视点不可能有这些性质。

### 渲染

自研的**等距 2.5D 渲染器**（`engine/render2d.ts`，Canvas 2D），选它而不是 WebGL 是因为没有着色器编译、没有 context lost、字体与 DOM 层共用同一套度量，加载后不会二次重排。

深度由画家算法 + 逐面背面剔除保证：所有几何都是凸长方体，正交投影下长方体边之间不会互相穿插，排序稳定，反向滚动不会闪烁。代价是没有逐像素深度缓冲——但这正是要求里"装配后允许被真实实体遮挡"要的行为。

**细节档**：由主体在屏幕上的高度决定（`detailFor`）。集群全景时关掉引脚、鳍片、风扇叶片——它们在 3px 时只是噪点，却是实打实的绘制开销。

### 文字与画面不打架

左侧文字轨是**固定的独立面板**，通过章节权重的交叉淡入淡出切换。这样在整条时间轴上文字都在屏幕上，不会像 `position: sticky` 那样在半章之后滑走到半屏以外。

Canvas 标注与主体**共用同一套相机矩阵**，所以标注永远贴在它所属的物体上。冲突用"不画"解决——标注不压到左侧文字栏、不顶出视口，这与文字栏宽度、镜头构图是同源的判断，不需要额外加底板。

进入 Agent 窗口时，同一套相机被**两种方式同时复用**：

- 层的位置由 `worldToScreen` 反解出目标世界坐标（正交投影闭式解），再按 `embed` 从"未变形位置"插值过去——因为插值起点是与 `p` 无关的固定值，所以反复抵达 `p=1` 不会累积偏移（`verify` 第 7 项：Δ = 0.0e+0）；
- Canvas 抬到窗口之上，用 CSS `clip-path` 裁进运行区。因此窗口内滚动、改变尺寸时主体都自然跟随，**不需要每帧同步**——与镜头解耦。

## 字体与章节设计

### 字体

- **中文正文与标题**：Noto Sans SC **可变字体**（`@fontsource-variable/noto-sans-sc`），`wght` 轴 100–900，**真实包含 700 字重**，不是把 400 假装成 700。
- **英文技术词 / 数字 / 代号**：Inter 可变字体（`@fontsource-variable/inter`），`font-variant-numeric: tabular-nums` 保证数字等宽。
- **回退链**：`Noto Sans SC` → `PingFang SC` → `Hiragino Sans GB` → `Microsoft YaHei` → `Source Han Sans SC` → `system-ui`。即使 webfont 未加载，中文仍有多个可用的中文无衬线字体，不会掉到衬线体。
- **授权**：两个字体包都是 **SIL Open Font License 1.1**，可合法分发，已随构建产物打包。
- **中文不加 `letter-spacing`**：方块字面自带间距，人为加字距会散。英文/数字走 Inter 的比例与基线，中英混排时不额外调整。

### 章节

每章有编号分类、**手动断行的中文标题**、服务说明、能力项（3–4 条）、交付内容（2 条带编号）。

- 标题断行是逐章设计的：中文方块字面宽，字号越大越需要手动分行，否则会在窄栏里出现孤字。标题的第二行通常落在动词或宾语上（"从一颗芯片 / **到一个 Agent**"），让断行本身产生语义的落差。
- 窄栏或矮视口下自动收字号与行高（`.is-dense`），而不是让文字溢出或被裁——用列宽/行高解决冲突，不是盖底板。
- 正文、能力项、交付结果分三组，层级清楚。能力项用 8×2px 的绿色短横做标记，交付内容用 `D1`/`D2` 等宽编号，视觉语言与工程主题一致。
- 全站没有"机械加粗"：只有标题（700）、小标题（600）、标签（600）和 D 编号（600）加粗，正文一律 400。

### 色彩

暖白 `#f6f3ec` / 墨黑 `#17181a` / 克制绿 `#1f7a4d`。绿色只用于强调、进度与电路板，正文里的绿色不超过 3%。PCB 绿（`#1d6b3f`）与银灰金属只出现在芯片上。

### 芯片造型

绿色基板 + 银色顶盖 + HUAWEI / Ascend 标记，参考昇腾风格。**属于概念造型，不对应任何一代产品的精确规格**——这一说明也写在第一章的正文里。

## 已知限制

1. **Canvas 2D 而非 WebGL**：在极低端设备上，靠填充率吃饭。已用细节档与 `devicePixelRatio` 上限（2）控制，但没有在真实低端设备上测量过。
2. **画家算法的排序限制**：正交投影下凸长方体不互相穿插，但如果将来加入非凸几何或需要逐像素遮挡，需要换成 WebGL 或加入深度缓冲。
3. **四层结构进入窗口时是等距视角压进矩形**：层在窗口里保持 2.5D 斜视角（只是缩小、移位），不是正交俯视。这保持了"同一套结构、同一套相机"的一致性，但也意味着它看起来是主场景的延续，而不是"运行区示意图"。
4. **执行流是示意性的**：信号沿预设的折线路径循环移动，它表达的是"数据在模型、工具、反馈之间流动"这件事，不是真实的调度时序。
5. **没有音频**。
6. **小屏放弃连续装配**：390×844 下是静态阅读布局（每章配一张等距示意图），不是缩小版的连续动画。这是明确的取舍，不是降级。
7. **第 08 章运行区内只画四层结构**：进入窗口后不再画芯片/板卡/服务器/机柜（那些在前面七章已经讲完），避免运行区里出现无关物体。

## 技术选型说明

**Vite + TypeScript + Canvas 2D**，无 UI 框架。

不用框架的原因：页面主体是一张 Canvas 加一层固定文字轨，DOM 结构简单且完全由我们控制，引入框架的收益不足以抵消它对渲染循环的干扰（框架的 diff 会与每帧的样式更新争夺主线程）。内容全部是静态数据，`content/chapters.ts` 直接导出对象，DOM 在启动时构建一次。

`verify` / `responsive` / `shots` 三个脚本依赖 Playwright，属于开发期工具，不进入构建产物。
